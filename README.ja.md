# sai-harness

> omp / エージェント納品システムに関する公開ノート:エビデンスに基づく完了 · チェックリストは常に最後

![sai-harness: omp 個人向け納品システムの公開ノート](assets/readme/hero.svg)

## 一言で言うと

[omp (oh-my-pi)](https://omp.sh) はターミナル向けのプログラマブルなエージェントシェルです — ハッシュ固定の編集、最適化されたツールハーネス、そしてシェルが動く場所ならどこでも動く TUI を備えています。その上に私は個人向け納品システムを構築しました:すべてのジョブはまず判定され — 軽い作業は単一パス契約(light contract)、重い作業は空コンテキストの reviewer を伴うマルチエージェントフロー — その後、分割してマージする(split-then-merge)方式で実行され、ディスク上のエビデンスに対して検証され(自己申告の「完了」は無効)、固定された絵文字5ブロックの骨格で人間に報告されます。メモリはひとつの曖昧な器ではなく3層に分割されています。危険な操作は意志力ではなくツールレベルで遮断されます。ルールが変わるときは、決定的な eval スイートが変更前後に実行されます。それらはすべて `AGENTS.md`、`skills/`、`agents/`、`extensions/`、`evals/` です — このリポジトリは、解説書であり、地図であり、境界線なのです。

## 何が違うのか

標準の omp インストールでも、コードを書き、コマンドを実行し、MCP を話し、有料エージェントを起動できます。私は二つ目のハーネスを発明したわけではありません。違いは規律(discipline)です:ジョブをどう判定するか、メモリをどう分割するか、複雑な作業をどう分割・統合するか、完了をどう立証するか、「まあ大丈夫だろう」を完了と数えるかどうか。この方法はツール非依存です。下記の omp 構築は、その具体化された、実際に動く一例です。

### 原則

1. **短い地図、深いフロー。** 上位ルールはルーティングのみを担い、重いプロセスはスキル(skills)に置く。起動時に読む地図は、実際に読める小ささを保つ。
2. **完了はエビデンスで示される。** ディスクの状態、コマンドの結果、検証のレシートが決める。「出来た気がする」プランは完了ではない。
3. **サブエージェントは専門化する。** 判定する者が QA をせず、QA する者が最終稿を書かず、書く者が自分自身をレビューしない。空コンテキストの reviewer が重い主張を監査する。
4. **メモリは分割される。** 作業メモ、失敗カード、知識ウィキ、デザイン/テーマライブラリはひとつの器ではない。各層はひとつのオーナーとひとつの形式を持つ。
5. **エラーは徹底的に死なせる。** 成果物を直すのは半分。根本原因 — ルールかチェック — も変え、再発すれば失敗するセンサーを残す。
6. **既存を先に探し、自作は後。** 車輪が検索できるなら、デフォルトでは再発明しない。
7. **同僚のように話す。** 結果を先に。自己検証とは、クリックし、リフレッシュし、聞き、見ること — コマンドの壁を押し付けることではない。
8. **デフォルトは分割して返す、会議しない。** 独立した調査/構築は並列で進み、結果はメインに返り、マージはディスク上に着地する。本当の議論か、大きな同種バッチだけがエスカレーションする。
9. **全体パッケージのみ。** 「やれ」はチェック済みプラン全体を意味し、アラカルトの半端な部品ではない。承認チケットの答えは正確に3つ:やる / プランを変える / 保留。

### クイックリファレンス:デフォルト vs 私の構成

| | デフォルト omp | この構成 |
|--|------------|-----------|
| 立ち位置 | 強力なターミナルコーディングエージェント | 個人向け納品ハーネス |
| メモリ | セッション + 自動ノート | 3層:作業 · 失敗カード · 知識ウィキ |
| 複数ステップのタスク | 任せたら走る | まず判定:軽量 vs 重量契約 |
| 複雑な並列処理 | 一人で全部やる傾向 | デフォルトで分割→返却、マージはファイルとして着地 |
| 完了 | 自己申告 | ディスクで検証。軽量 = 自己検証、重量 = 独立レビューア |
| リサーチ | 場当たりな検索 | 検索スキルによる浅/深の2段階 |
| エラー後 | 同じ箇所を直す | 成果物 + 根本ルール + チェックを直す |
| 人間への報告 | 構造が崩れる | 固定5ブロック骨格、チェックリストは常に最後 |
| ハーネス変更 | 感覚任せ | ゴールデン evals のベースライン → 差分を前後で |
| 規模 | クリーンなシェル | 数十のスキル、6種のエージェント型、ハードゲート |

## コア手法

### アーキテクチャ

```
You
 └─ Main control session (reads AGENTS.md map, judges, dispatches, closes out, writes back)
     ├─ Judging: light → chain/loop; heavy → multi-agent flow + empty-context reviewer
     ├─ Rules: AGENTS.md (short map) + contracts (light / heavy) + snapshot-layer rules
     ├─ Memory: working memory ↔ MaxKB-like mistake cards ↔ wiki knowledge graph
     ├─ Agents: task / scout / reviewer / designer / sonic / librarian
     ├─ Skills: entry for design, media, remote, knowledge, evolution
     ├─ Hard guards: delete-guard, path-guard (tool-level, block not warn)
     ├─ Eval: golden suite with baseline → delta on every harness change
     └─ Interfaces: browser, terminal, design/theme/library, message bridge
```

### 判定とオーケストレーション(シェルを替えない)

オンラインの「エージェントグラフ」の話は、たいてい要約するとこうです:全部自分でやるな、やるべき時に分割せよ、分割したら統合せよ、そして統合の着地を見届けよ。

私は外部のグラフエンジンに乗り換えませんでした。**2つの契約(contracts)** と、その前に立つ判定者(judge)を書いたのです:

| 仕組み | いつ | 保証すること |
|---|---|---|
| **判定 / ルーティング** | すべてのジョブの最初のステップ | タスクを分類し、誰が働くかを決め、シングルスレッドのメイン制御を保つ |
| **軽量契約 (light contract)** | 小さく、低リスク、ファイル数が少ない | ステージ依存を持つタスクエンジン。機械的な自己検証で十分 |
| **重量契約 (heavy contract)** | それ以外のすべて | マルチエージェントのファンアウト、空コンテキストの reviewer、主張へのゲート |
| **分割して返す (split-and-return)** | 独立した調査/構築 | サブエージェントが並列実行し、結果はメインセッションに返ってマージされる |
| **マージゲート** | 複数パスの作業 | 複数の並列パスが、会議の要約ではなくディスク上の統合物を生み出さねばならない |
| **戦争会議へのエスカレーション禁止** | 単純なジョブ | 些細な質問に重いトポロジーを強制するのは判定者がブロックする |

体感:複数ステップの作業は安定し、エビデンスを返す。小さなことは、委員会を招集する代わりにシングルスレッドのまま。

### 完了:エビデンスがすべて

完了に見えるジョブも、次の条件が揃うまで完了ではない:

1. **実行される / 観察可能** — 終了コードが通り、ファイルは主張された場所に存在する
2. **人間が確かめられる** — 成果物を開き、完全なパスを報告し、長い実行は進捗を報告する
3. **Todo がゼロ** — 未処理のチェックリスト項目がない(チェックリストのビューは自分で確認する)
4. **沈殿させる (sinking)** — 教訓・決定が、その真実の置き場所(ウィキ / 失敗カード / テンプレート)に着地している
5. **重量の場合:reviewer 承認** — 独立した空コンテキスト reviewer、クロスモデル

クラッシュには**二重修正 (double fix)** が必要です:この成果物を直す*かつ*根本原因(ルールかチェック)を直す。ファイルにパッチを当てて先に進むのはカウントされません。

### 報告の骨格(人間と話す)

各メッセージは作業指示書です。納品は固定5ブロックの骨格で、順番どおりに、**チェックリストは常に最後**に:

| ブロック | 内容 |
|---|---|
| 🎯 一行の結果 | 完了 / 結論 / どこで詰まったか |
| 🧩 人間向けの説明 | 何が起きたか、どう対処したか、明示的にやらなかったこと |
| ✅ 効果と自己検証 | 何を感じるか + どう確認したか(クリック / リフレッシュ / 聞く / 見る) |
| 👉 次のステップ | 閉じられる?そう言う。足りない?完全な次の具体的ステップ |
| 📋 チェックリスト(常に最後) | 検証者 / todo / メモリ / ウィキ — エージェント自身の監査であり、「了解」の頷きではない |
| (必要に応じて追加) | 開く場所、全文の場所、リスク、署名… |

選択肢は、提示するとき、それぞれ説明します(意味 / コスト / どうゴールを満たすか)。プランは全体パッケージで出荷され、アラカルトのメニューにはなりません。

### メモリ:3層

| 層 | オーナー | 形式 | 実用的な用途 |
|---|---|---|---|
| **作業メモ (Working memory)** | エージェントバンク | 最近の記録 + 選好ルール | セッション冒頭のコンテキスト |
| **失敗カード (Mistake cards)** | MaxKB 風カード | 短い教訓 + 再発フィンガープリント | 似た過去作業を最初に確認する |
| **知識グラフ (Knowledge graph)** | ウィキ / 長文形式 | トピックごとに現行版1つ | 調査とマニュアルはここ。旧版は履歴へ |

デザイン、トピック、再利用可能なデモには専用のテーマライブラリがあり、実際に使われたものだけを受け入れます。エージェントは自分でメモリに書き戻します。同じ質問は二度されません。

### レジリエンスと安全性

- 危険な git、破壊的な削除、キーの直接読み取り:**ツールレベルの遮断**であり、警告ではない。
- シークレット:暗号化管理パイプライン。キーが会話本文やログに入ることはない。
- 圧縮後、重要なルールは再注入される。地図は読み直せる小ささを保つ。
- スナップショットとアーカイブは第一級市民:大きな編集の前にはバックアップ。ゴミは単一のアーカイブルートへ。
- ゴールデン eval スイートがハーネス変更のたびにベースライン → 差分を実行。リグレッション = 完了ではない。

### 外を見る

外部検索、ブラウザ、リモート操作、定期ジョブ:これらはすべてハーネスに生えた触角であり、第二の脳ではない。新しい実装:既存を先に探す(オープンソースを優先)、何も合わないときだけ自作し、何を検索してなぜ使わなかったかを書き留める。

## このリポジトリ

**あるもの** — 本解説、能力マップ、ヒーロー画像、サニタイズ済みでそのままコピーできるテンプレートとチェックリスト（`templates/`、`checklists/`）：短い地図 `AGENTS.md` スケルトン、2つの契約（light / heavy）、scout と reviewer の2つのエージェント定義、evals 基線スクリプト、完了定義チェックリスト、報告スパインチェックリスト。

**ないもの、そして今後もないもの**
- API キー、Cookie、トークン、アカウントプール
- 内網アドレス、プライベートホスト名、顧客データ
- 私の本番環境に接続する設定
- 「これをインストールすれば私と同じ強さになれる」スクリプト — 方法はコピー可能ですが、あなたの失敗と筋肉はコピーできません

## テンプレートとチェックリスト

サニタイズ済みのスケルトン。新しいエージェントリポジトリにドロップして改编するだけ。これらが運ぶのは*手法*であり、私のプライベート設定ではない — パス、キー、ホスト名、内部スキル名は一切残っていない。

| ファイル | 何が得られるか |
|------|----------------|
| [`templates/AGENTS.md`](templates/AGENTS.md) | 短い地図テンプレート:鉄のルール + ルーティング、手順は名前参照のみでコピーしない、毎ターン5つの規律、レッドライン、報告スパイン、自己メンテナンス |
| [`templates/light-contract.md`](templates/light-contract.md) | light タスクエンジン:3行 spec、`task` ディスパッチ、機械的自己検証（light たる理由）、done 5件、heavy へ昇格するタイミング |
| [`templates/heavy-contract.md`](templates/heavy-contract.md) | heavy マルチエージェント契約:完全 spec テンプレート、役割別ディスパッチ（scout/task/reviewer）、ウォッチドッグレール、独立 reviewer 入り done 5件、中止ルール |
| [`templates/agents-scout-reviewer.md`](templates/agents-scout-reviewer.md) | 2つの要となる役割のコピー可能なエージェント定義:`scout`（読み取り専用の高速偵察）と `reviewer`（空コンテキスト、クロスファミリー、ディスク証拠の評決） |
| [`templates/evals-baseline.ps1`](templates/evals-baseline.ps1) | PowerShell evals ハーネステンプレート:ファイルに対する純粋なアサーション、ルール変更前に基線スナップショット、変更後に diff — `fail>0` または pass 数低下で回帰。コアファイルサイズガード付き |
| [`checklists/completion-dod.md`](checklists/completion-dod.md) | 「本当に終わったか」のチェックリスト:5つの必須次元、タスクタイプ別テーブル、DoD レッドライン、「分からない」と「同じエラー3回」の硬ルール |
| [`checklists/reporting-spine.md`](checklists/reporting-spine.md) | 報告スパインチェックリスト:5つの固定ブロック順序、チェックリストは常に最後、受領文字列はツール応答からコピーのみ、語彙ゲートとオプションゲート |

## クイックスタート

公式の拡張ポイントの上に積み上げる:

| ステップ | やること |
|------|-----------|
| 1 | 短く硬い `AGENTS.md` を書く:鉄のルール + ルーティング表。重いフローはファイルに置く |
| 2 | 判定者を追加する:ジョブがどの契約を使うか決める(light/loop か heavy/multi-agent) |
| 3 | 繰り返しフローをスキルに分割する(まず delivery、search、evolution) |
| 4 | 読み取り専用エージェントを2つ追加する:scout(調査)と reviewer(主張の検証) |
| 5 | 最も恐れる失敗は、散文ではなく拡張機能で溶接して塞ぐ |
| 6 | メモリを分割する:作業 vs 失敗 vs 知識 — 3ファイル、3オーナー |
| 7 | 完了 = 観察可能なエビデンス + 人間の声。自己申告の「完了」は無効 |
| 8 | 同じエラーが2回 → ルールを変え、再発すれば失敗するチェックを残す |
| 9 | 報告の骨格を直す(結果 → 平易な言葉 → 検証 → 次 → チェックリストは常に最後) |
| 10 | 地図を変える前に evals のベースラインを取り、変更後に再実行する |

公式資料:
- [oh-my-pi (omp)](https://github.com/can1357/oh-my-pi) — 私が土台にしているターミナルハーネス
- [omp.sh](https://omp.sh) — プレイヤー向けリファレンス
- [AGENTS.md spec](https://agents.md) — 多くのシェルが理解する地図ファイル形式

**こんな人向け** — ターミナルエージェントを長期運用していて、自分のワークフローを公開・磨き上げたい人。レイヤリング(方法論、契約、実行器、データ)はどこにでもコピー可能。閲覧だけの訪問者は、Architecture + Principles で十分。

**向いていない人** — ワンクリックインストール派、キー/アカウント漁り、あるいはこれを何らかの会社の公式ドキュメント扱いする人。ここには何もない。
